# 第 2 课：一个自动工作流如何贯穿前端、后端和数据库

本课对应已经可以实际运行的“自动工作流”模块。你可以一边打开页面操作，一边对照代码理解完整请求链路。

## 1. 先区分工作流模板和运行记录

`Workflow` 是可以反复使用的模板，保存名称、说明、颜色和步骤定义。例如“爆款内容流水线”包含目标分析、标题、脚本和质检四步。

`WorkflowRun` 是某次真正执行留下的记录，保存本次输入、每一步状态、输出、开始时间和完成时间。同一个模板可以产生很多条运行记录。

这和工厂很像：生产线设计图是模板，每一批产品的生产单是运行记录。把两者拆开后，系统才能统计运行次数、查看历史结果和重试失败任务。

## 2. 点击“开始运行”后发生了什么

```text
WorkflowPage.tsx
  └─ superstaffApi.runWorkflow()
       └─ POST /api/v1/workflows/{id}/runs
            └─ WorkflowService.run_workflow()
                 ├─ WorkflowRepository：读取模板、保存运行状态
                 ├─ WorkflowExecutor：执行每一个步骤
                 └─ SQLite：持久化结果
```

前端先在 `WorkflowPage.tsx` 收集用户输入，再由 `src/api/superstaff.ts` 把 TypeScript 对象转换成 HTTP JSON 请求。前端只负责表达“我要运行”，不会自己伪造完成状态。

后端路由 `app/api/routes/workflows.py` 校验输入后调用服务。`WorkflowService` 决定步骤如何从 `pending` 进入 `running`，最后进入 `done`；仓储负责数据库读写；执行器只关心每一步怎样产生结果。

这种拆分让我们以后接入真实模型时，只需新增执行器适配器，不必重写页面、路由或数据库。

## 3. 为什么需要类型和接口契约

前端 `src/types/contracts.ts` 与后端 `app/schemas/workflows.py` 描述了同一份数据：工作流有哪些字段、步骤长什么样、运行状态有哪些值。

它们不是重复劳动，而是接口两端各自的安全检查：

- TypeScript 在前端编译时发现字段拼错。
- Pydantic 在后端运行时拒绝不合法的请求。
- API 测试确认真实返回仍符合约定。

这就是面试中常说的“前后端通过 API 契约协作”。

## 4. 这一模块分别证明了哪些工程能力

前端：React 状态管理、表单、弹窗、异步请求、加载与错误状态、响应式 CSS。

后端：REST API、业务服务、依赖注入、状态机、异常转换和分层架构。

数据库：模板与运行记录建模、一对多步骤、事务写入、级联删除和索引。

测试：后端覆盖预置工作流、自定义创建、运行、持久化、删除和输入校验；前端执行类型检查、单元测试和生产构建。

## 5. 你现在应该能回答的面试问题

1. 为什么不能只在浏览器 `localStorage` 保存工作流？
2. `Workflow` 和 `WorkflowRun` 为什么必须分成两个对象？
3. 前端为什么不能直接把运行状态改成 `done`？
4. 路由、服务、仓储和执行器分别负责什么？
5. 如果模型执行需要两分钟，同步接口会有什么问题，下一步如何改？

第五题的答案是：请求会长期占用连接，页面也无法持续获得细粒度进度。正式版应把执行交给后台任务队列，通过 SSE 或 WebSocket 推送进度，并增加超时、重试和取消。
