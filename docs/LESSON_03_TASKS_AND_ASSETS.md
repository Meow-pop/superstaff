# 第 3 课：为什么任务和成果要分开建模

这一课对应正式版的“任务中心”和“成果资产”。它解决的是超级员工系统里一个非常关键的问题：AI 完成一次任务后，结果不能只留在聊天窗口里，而要变成可以追踪、搜索和继续使用的企业资产。

## 1. 任务中心为什么需要统一读模型

系统现在有两种执行来源：

- `Job`：用户把目标交给一名 Agent。
- `WorkflowRun`：用户运行一条自动工作流。

它们的数据库结构不同，但任务中心需要用同一张列表展示标题、来源、状态、步骤、进度和结果。因此后端没有让前端自己拼接两组数据，而是由 `TaskCenterService` 生成统一的 `TaskCenterItem`。

```text
jobs ───────────┐
                ├─ TaskCenterService ── GET /api/v1/tasks ── 任务中心页面
workflow_runs ──┘
```

这种专门为查询页面准备的数据结构叫“读模型”。它不会取代原始领域对象，只负责把不同来源投影成页面需要的统一形状。

## 2. 交付物和成果资产有什么区别

`Artifact` 是一次 Agent 任务内部的交付物，主要用于任务详情和人工验收。

`Asset` 是进入企业成果库、可以跨任务复用的内容。它记录：

- 来自 Agent 任务还是工作流运行；
- 原始任务 ID 和执行来源；
- 成果类型、标题、正文和标签；
- 当前处于使用中还是已归档；
- 创建和最近更新时间。

目前任务或工作流成功后会自动创建一份 `Asset`。这样任务记录负责回答“这次工作发生了什么”，资产记录负责回答“哪些结果以后还能继续用”。

## 3. 跨模块流转为什么不是直接调用视频生成

素材管家中的“创意视频”“多场景剪辑”和“发布管家”按钮会创建一条 `AssetHandoff`：

```text
成果资产 → 创建流转任务 → queued → 目标模块后续处理
```

第一版只创建可追踪的排队记录，不会假装外部平台已经执行完成。以后接入真正的视频模型或发布平台时，后台执行器消费这些记录，并把状态更新为 `processing`、`done` 或 `failed`。

这种设计有三个好处：

1. 页面请求不需要等待几分钟的视频生成。
2. 每次外部动作都有来源和状态，可以重试和审计。
3. 发布等高风险动作可以在执行前增加人工确认。

## 4. 一次成果流转如何穿过全栈

```text
AssetCenterPage.tsx
  └─ superstaffApi.createAssetHandoff()
       └─ POST /api/v1/assets/{id}/handoffs
            └─ AssetService.create_handoff()
                 ├─ 检查资产存在且未归档
                 └─ AssetRepository 写入 SQLite
```

前端只发送资产 ID、目标模块和备注。后端负责检查业务规则并决定初始状态，数据库负责持久化。页面刷新后仍能看到流转记录，证明它不是临时前端状态。

## 5. 数据库设计里值得关注的点

- `assets` 对 `(source_type, source_id, kind)` 建唯一约束，防止同一次执行重复沉淀相同类型成果。
- 常用的状态与时间查询使用组合索引。
- `asset_handoffs.asset_id` 是外键，保证流转记录一定属于真实资产。
- 老版本任务成果会在启动时安全迁移到新资产表，不删除旧数据。
- 初始化完成后运行 `PRAGMA optimize`，帮助 SQLite 选择合适的查询计划。

## 6. 面试时可以怎么讲

你可以这样回答“这个模块是如何设计的”：

> Agent 任务和工作流运行属于不同领域对象，我在后端增加统一读模型供任务中心查询，避免前端耦合两套内部结构。执行完成后，系统把交付物沉淀为独立资产，再通过可追踪的 Handoff 记录交给视频、剪辑或发布模块。数据使用 SQLite 持久化，并通过唯一约束、外键和索引保证一致性和查询效率。
