# 第 4 课：从成果资产到视频与发布计划

M3 把之前的成果流转记录变成了真正可操作的制作任务。成果资产不再停留在素材库，而是可以进入脚本、分镜、本地视频渲染、账号选择和发布时间编排。

## 1. 为什么 Handoff 和 ProductionJob 要分开

`AssetHandoff` 记录用户的业务意图：“把这份成果送往创意视频”。

`ProductionJob` 记录目标模块如何执行，包括状态、脚本、场景、输出、账号和计划时间。

```text
Asset → AssetHandoff → ProductionJob → 制作 / 审核 / 排期
```

分开以后，一份交接记录不会被某个具体视频供应商绑死。以后可以保留相同 Handoff，再根据配置选择本地渲染、云端视频模型或人工剪辑。

## 2. 制作任务状态机

```text
queued → running → review → done
   └──────────────→ failed → running
```

- `queued`：成果已经进入目标模块。
- `running`：执行器正在生成脚本与场景。
- `review`：方案完成，等待人工审核。
- `done`：用户确认制作方案。
- `failed`：执行失败，可以重试。

发布任务使用 `ready` 表示账号和时间已经配置完成，但它不等于“平台发布成功”。真实发布需要平台授权、人工确认和平台回执。

## 3. 本地演示视频怎样生成

正式前端使用浏览器原生能力生成 WebM：

1. Canvas 按场景绘制竖版画面、标题、字幕和进度条。
2. `captureStream()` 把 Canvas 转换成视频流。
3. Web Audio 创建一条基础音轨。
4. `MediaRecorder` 合并视频和音频。
5. 浏览器生成 Blob 并下载到本地。

这条路径证明“任务结果可以变成真实媒体文件”，但不把画面和声音质量当作超级员工的核心。正式产品可以在执行器层替换为高质量视频和语音供应商。

## 4. 为什么账号表不保存密码

`SocialAccount` 只保存平台、账号名称、公开标识、状态和统计数据。系统不保存密码、Cookie 或临时登录信息。

正式接入平台时，应使用平台 OAuth 或官方 API：

- 令牌只保存在后端的安全存储中；
- 前端只能看到授权状态；
- 发送或发布前必须经过人工确认；
- 平台返回的任务 ID 和错误信息要进入审计记录。

## 5. 一次发布计划如何穿过全栈

```text
PublishingCenterPage
  └─ POST /production-jobs/{id}/schedule
       └─ ProductionService.schedule_publish()
            ├─ 检查任务类型
            ├─ 检查账号存在且未停用
            └─ SQLite 保存账号、时间和 ready 状态
```

页面刷新后计划仍然存在，说明账号和排期属于后端业务数据，而不是临时页面状态。

## 6. Docker 解决了什么

开发模式需要分别启动 React 和 FastAPI。Docker 把它们封装成两个可以协同运行的服务：

- Nginx 提供编译后的前端并代理 `/api`。
- FastAPI 负责业务接口。
- SQLite 位于持久数据卷中。

这让其他人不需要了解项目目录，只需构建并启动容器。但 Docker 不是 Windows `.exe`，完全离线桌面安装仍需要后续封装。
